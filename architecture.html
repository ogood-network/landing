Proposed Architecture on Cloudflare

Hosting Ogood volunteer federation nodes on Cloudflare's developer platform

📅 Prepared 21 October 2026 📋 Implementation handover ⚠️ Not yet deployed

Summary: Ogood can run as one custom Worker on the apex domain ogood.network, serving both the website and ActivityPub, with D1 as the source of truth, Queues as the delivery pipe and R2 for media. Cloudflare has no graph database, and Ogood does not need one to start: model the links explicitly in D1 and add a graph layer only if multi-hop trust queries become a real workload.

Status: this note has not been sent to any Cloudflare worker or agent, and nothing has been deployed.

What Ogood does

  • Federates volunteering opportunities from the providers who own them. The provider controls the source; Ogood stores a discovery index that points back to it.
  • Phase 1Scraped imports: Ogood lists public opportunities from provider websites as provisional entries.
  • Phase 2Provider adapters: providers push changes (signed webhooks) or publish a normalised pull feed that Ogood polls.
  • Phase 3First-class provider servers: providers run their own ActivityPub actors; Ogood follows them, migrates their accounts and rebuilds the catalog from their outboxes.
  • Discovery by provider, location and date.
  • History: every event keeps a permanent link, with photos, check-ins and attestations. Past and cancelled events stay visible and are clearly separate from upcoming ones.
  • Later: two-party signed completion claims between a volunteer and a provider.

What this replaces from the Mastodon-style stack: no PostgreSQL, no Redis, no Elasticsearch, no Linux VMs.

Things to know before building

  • D1 is SQLite, not PostgreSQL. There is no JSONB type and no PostGIS. D1 does support the SQLite JSON extension, FTS5 full-text search and math functions. Store raw ActivityPub and signed-claim payloads as JSON text columns and index the relational fields beside them.
  • Vectorize is not a search engine replacement. It finds semantically similar text. Keyword search (FTS5), radius search (latitude and longitude ranges) and date filters stay in D1. Vectorize is an optional extra on top.
  • Durable Objects are optional. Cloudflare describes them as the tool for global coordination and strongly consistent per-object state. Ogood's MVP can do without them.
  • Queues, not KV, for delivery. Cloudflare's guide says to use Queues when each message is a unit of work to be completed, retried and tracked individually — which is exactly a federation delivery.
  • Hyperdrive only matters if you later want an external PostgreSQL or MySQL database. It is not part of this design.

Domain and routing

One Worker answers on the apex, ogood.network, over normal HTTPS on port 443. ActivityPub is ordinary HTTP with JSON-LD bodies, so there is no separate port, no protocol upgrade and no mandatory subdomain. A media subdomain for R2 can be added later if useful.

Endpoints

  • /.well-known/webfinger — resolves handles such as acct:provider-slug@ogood.network to actor URLs
  • /.well-known/nodeinfo + NodeInfo document — lets other servers identify the software
  • Instance actor (Application type), e.g. /actor — signs fetches made by Ogood itself
  • Provider actors (Organization type), e.g. /providers/{slug} — each with inbox, outbox and followers collections
  • Shared inbox at /inbox — remote servers deliver once per server, not once per follower
  • Opportunity objects, e.g. /opportunities/{id}, and dated sessions, e.g. /opportunities/{id}/sessions/{session-id}

Content negotiation

The same URL returns JSON-LD when the request's Accept header asks for application/activity+json or application/ld+json with the ActivityStreams profile, and HTML otherwise. Send Vary: Accept so caches keep the two apart, and include a link rel="alternate" to the JSON form in each HTML page.

Custom Worker, not Mastodon hosting

Ogood is a purpose-built ActivityPub service. It does not host Mastodon and does not need Mastodon's client API. Mastodon itself expects Rails, PostgreSQL, Redis and background workers on servers. Cloudflare's own Mastodon-compatible experiment on Workers, Wildebeest, is archived and no longer maintained, so it is not a base to build on.

The Fedify framework has a Cloudflare Workers package (@fedify/cfworkers) that handles WebFinger, HTTP signatures and delivery, using KV and Queues. It needs the Workers Node.js compatibility flag. Worth evaluating before hand-rolling signatures.

Data model in D1

Core tables

  • providers — id, slug, display name, website, status (provisional, claimed, verified), source kind (scraped, adapter, federated), canonical actor URI once the provider runs its own server, claim and consent notes
  • provider_sources — where each provider's data comes from, last fetch time, ETag and content hash
  • opportunities — id, provider, authoritative source URI, title, description, publish start and end, status, raw source JSON, content hash, first seen, last seen, updated
  • roles — per opportunity, mirroring the standard's Role (commitment, apply link, age limits, remote participation, skills, requirements)
  • sessions — id, opportunity, start and end in UTC, original time zone, recurring weekly slot when only that is known, location, status (scheduled, cancelled, postponed, completed), permanent URL
  • locations — name, free-text address, latitude, longitude, an indexed grid or geohash column for radius search, optional WKT geometry, remote flag
  • causes, skills, requirements — join tables to the standard's taxonomies
  • media — R2 object key, owner, session, consent flags
  • checkins and attestations — who, which session, when, how verified
  • claims (later) — session, volunteer actor, provider actor, claim JSON, each party's signature, status

Federation tables

  • remote_objects — cached remote actors and objects by URI, with raw JSON and fetch time
  • inbox_activities — activity ID as a unique key, actor, received time, processing status. This is what makes inbound processing idempotent
  • outbox_activities — every activity Ogood publishes, with its JSON
  • deliveries — one row per activity per target inbox: status (pending, sent, failed, dead), attempts, next attempt time, last error
  • followers — actor followed, follower URI, inbox, shared inbox
  • actor_keys — public keys in D1. Private keys in Workers secrets, or encrypted in D1 with a key held as a secret

Past versus upcoming is derived from each session's end time and status. Nothing is deleted: a past session keeps its URL, photos and attestations; a cancelled session keeps its URL with status cancelled and is announced to followers as an Update, not a Delete.

Fit with the Volunteering Data Standard

What the Volunteering and Social Action Ontology at volunteeringdata.io actually defines:

  • Organisation — name, description, website, image, causes, charity registrations, activities
  • Activity — title, description, image, publishStart, publishEnd, organisation, roles, sessions, emergency flag
  • Role — title, description, commitment, apply link, remote participation, minimum and maximum age, accessibility, requirements, rewards, skills
  • Session — a time and place for an activity. The standard notes that sessions usually have no ID of their own, because they are embedded in the activity
  • Location — name, free-text address, latitude, longitude, and a GeoSPARQL geometry (e.g. a council boundary as WKT)
  • Time — modelled with OWL Time. The standard predefines weekly slots such as MondayMorning (6 AM to 12 PM), MondayAfternoon (12 PM to 6 PM) and MondayEvening (6 PM to midnight), and recommends reusing them. Custom times use hasBeginning and hasEnd

Gaps for Ogood

  • The examples describe recurring weekly availability, not one-off dated events. Ogood needs concrete start and end date-times for sessions.
  • There is no status property for cancelled or postponed sessions.
  • Sessions need their own stable IDs, because Ogood gives every event a permanent link with photos and check-ins.
  • Check-ins, attestations and completion claims are outside the standard.

Recommendation: use the standard's Organisation, Activity, Role, Location and taxonomies as the backbone, and add a small Ogood extension for dated sessions, session IDs and status. For fediverse compatibility, also publish each session as an ActivityStreams Event with startTime, endTime and a Place location, alongside the standard's context. Raise the dated-session and status gaps in the standard's GitHub discussions.

Federation pipeline

Outbound

  1. A catalog change, the outbox activity and its delivery rows are written together in one D1 batch.
  2. Each delivery ID goes onto a Queue as a small message. The database row is the record; the queue is only the mail truck.
  3. The consumer signs the request (HTTP Signatures; support the draft-cavage scheme Mastodon uses and plan for RFC 9421) and POSTs to the target inbox, then updates the delivery row.
  4. Failures retry with backoff, and the next attempt time is written to the row.
  5. A Cron Trigger sweeper re-enqueues any delivery still pending past its next attempt time. This covers messages that expire from the queue: retention is 24 hours on Workers Free and 4 to 14 days on Workers Paid. After a set number of days, a delivery is marked dead.

Inbound

  1. Verify the HTTP signature against the sender's public key (fetched, then cached). Reject unsigned or invalid requests.
  2. Insert the activity ID into inbox_activities. A duplicate ID is acknowledged and dropped.
  3. Return 202 Accepted and process from a Queue.
  4. Handlers are idempotent: upserts keyed by object URI, and an Update older than the stored version is ignored.

Imports and adapters

  • Scrapers run on Cron Triggers, put one job per source on a Queue, normalise to the standard and upsert. Compare content hashes first so unchanged records cost no writes.
  • Push adapters: providers call a signed webhook (HMAC per provider).
  • Pull adapters: Ogood polls a normalised feed with ETag or If-Modified-Since.

Trust, privacy and security

  • Never impersonate a provider. Scraped providers appear as Ogood listings, clearly labelled "listed by Ogood from a public source", with a link to the original. They do not post as if the provider were speaking.
  • Permission: list only public information, respect site terms and robots rules, honour takedown requests quickly, and offer a claim flow that turns a provisional listing into a verified one.
  • Personal data: do not scrape volunteers' names or contact details. Photos and check-ins need consent, and location metadata should be stripped from uploaded photos.
  • Remote fetches: limit response sizes, allow only HTTPS, and validate hosts before fetching.
  • Rate limiting per remote host, using a Durable Object if needed.
  • Signed claims prove who asserted something, not that it happened. Show them as "confirmed by both parties", never as proof.
  • Migration: when a provider moves to its own server, link the accounts (alsoKnownAs and a Move activity), redirect Ogood's old URLs, and rebuild the catalog from the provider's outbox.

Graph or relational

Cloudflare has no graph database. Its storage guide lists Workers KV, R2, Durable Objects, D1, Queues, K2, Hyperdrive, Basin Pipelines, Analytics Engine and Vectorize, and none of them is a graph store. A graph database would mean an external hosted service called over HTTP from the Worker. Hyperdrive only accelerates PostgreSQL and MySQL.

Recommendation: stay relational in D1. Graph is not automatically better for this data:

  • The queries are shallow. Most of Ogood's reads are one or two hops with filters: opportunities near here, this month, from this provider. Indexed SQL is very good at this.
  • The graph already lives in the identifiers. The data is linked data: every provider, opportunity and session is a URI. That gives you a graph without needing a graph engine.
  • Deeper walks are still possible. SQLite supports recursive queries (WITH RECURSIVE), which cover moderate traversals such as provider networks or chains of attestations.
  • A second database adds cost. It means another vendor outside Cloudflare, another bill and a sync job to keep in step.

When a graph layer would earn its place: multi-hop trust and reputation across volunteers, providers and attestations; "people who volunteered here also volunteered at" recommendations; or community detection across the network. The path there is cheap: keep an edges table in D1 (subject, predicate, object) as you go, and if those queries become central, project it into a graph or RDF store as a derived read model. Because the standard is RDF, a triple-store export is a natural fit.

Verdict: a prototype fits on Workers Free. Every core product in this design is available there. The limits that would bite first:

  • Queue operations: Queues counts a write, a read and a delete for each message, so 10,000 operations a day is roughly 3,300 messages. One update fanned out to 500 inboxes is 500 messages; shared inboxes reduce this.
  • CPU time: 10 ms of CPU per invocation may be tight for signing, signature verification and JSON-LD handling. Measure it early.
  • D1 writes: scrapers can burn through 100,000 rows written a day unless unchanged records are skipped by content hash.
  • Queue retention: 24 hours on Free makes the cron sweeper essential, not optional.

Move to the $5 plan when real federation fan-out starts.

Build order

  1. Worker on ogood.network serving the website and a read-only catalog from D1, with scraped imports, FTS5 keyword search, location search and date filters.
  2. ActivityPub read side: WebFinger, NodeInfo, the instance actor, labelled provisional provider actors, opportunity and session objects with content negotiation, and outboxes.
  3. Follows, the delivery ledger, the Queue consumer and the cron sweeper.
  4. R2 media, check-ins and attestations.
  5. Provider adapters (push and pull) and the claim flow.
  6. Later: provider-run servers and migration, two-party signed completion claims, Vectorize semantic search, and a graph projection if needed.
